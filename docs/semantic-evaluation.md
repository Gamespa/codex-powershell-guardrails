# Semantic evaluation

Semantic checks execute proposed commands against disposable inputs and compare
their effects with repository-owned assertions. Syntax, discovery, and semantic
results are separate. Passing these fixtures does not establish correctness for
every task, and unimplemented validators are never counted as passes.

## Current coverage

`tests/model-cases.json` assigns `{ "id": "...", "version": 1 }` in the optional
`validator` field. Unknown validators, unsupported versions, non-PowerShell cases,
and extra validator fields fail preparation. Validator code is maintained in
`scripts/lib/semantic-fixtures.psm1`; it is not generated by the evaluated model.

| Case | Validator | Observable checks |
| --- | --- | --- |
| modern_native_quotes | native-arguments | Empty, quoted, spaced, Unicode and trailing-backslash arguments in Windows and Standard modes |
| binary_redirection | binary-output | Exact random archive bytes, separate diagnostics, success and nonzero exporter exits |
| search_status | search-status | Matching, nonmatching and missing directories; distinguish real failure and retain caller preferences |
| windows_rg_file_glob | json-search | Nested JSON hits, paths with spaces, exclusion of matching text files |
| structured_output | json-array | Zero/one/three items, deeply nested values, Unicode, nulls, booleans and arrays |

Two reproducible seeds (1729 and 7919) vary data and names, producing 22 trials for
the five supported cases. Each trial uses a fresh container. Prompts include a
public execution contract describing supplied variables and output formats, but
not expected results, seeds, or assertion code. This contract changes prompts;
compare all candidate arms under the same updated cases. Fixtures for SSH, remote
services, authorization decisions and policy explanations are not implemented.

## Execution boundary

Requirements: a provisioned Docker Windows engine supporting Hyper-V isolation
and a trusted local Windows image with `pwsh.exe` 7.6+ and `rg.exe` on PATH, usable
by `ContainerUser`. Provision the image separately, with no embedded credentials.
The evaluator does not install Docker, enable Windows features, build images,
pull images, or use the host shell as a fallback.

The backend resolves the supplied local image to an immutable image ID. It
creates a container with Hyper-V isolation, no network, a 1 GiB memory limit,
one CPU, and `ContainerUser`. No host directories, credentials, or sockets are
mounted. Images declaring volumes are rejected. Container configuration is
checked before startup; a process-isolated container is rejected. This choice
uses Microsoft's documented [Hyper-V isolation boundary](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-security)
and Docker's [container creation controls](https://docs.docker.com/reference/cli/docker/container/create/).

Only a generated input bundle is copied into the container; expected values stay
outside it. The worker checks the runtime and tools, then runs the answer in a
child process with a 20-second deadline. Output previews and named artifacts are
bounded at 64 KiB each. The outer operation also has a deadline. The container is
removed after success or failure, with an ownership label checked before removal.
An unverifiable or failed cleanup is an infrastructure error with its container
name retained for inspection. No untrusted output directory is copied to the host.

The protocol and assertions are behavioral tests, not an adversarial proof that
an answer could never inspect or manipulate its in-container harness. Isolation
protects the host; distinct seeds and host-side expected values improve evaluation
quality. Backend/protocol failures must not be interpreted as model quality scores.

## Running

To evaluate existing `answers.json` without making another model call, supply a
trusted image already present in the Windows engine and a fresh output directory:

```powershell
pwsh -NoLogo -NoProfile -NonInteractive -File ./scripts/evaluate-semantics.ps1 `
  -AnswersPath ./artifacts/example/updated-1/answers.json `
  -Image guardrails-eval:local -OutputDirectory ./artifacts/semantic-example
```

Use `-CaseIds` to select the cases represented in a partial answer file. Supported
cases with missing or empty commands fail; cases without validators are skipped.

To generate answers and then evaluate their semantics in one run:

```powershell
pwsh -NoLogo -NoProfile -NonInteractive -File ./scripts/evaluate-model.ps1 `
  -Variants updated -SemanticImage guardrails-eval:local
```

Without `-SemanticImage`, model evaluation continues to propose commands only,
and semantic statuses are `not-evaluated`. With an image requested, a missing
backend or unavailable image yields `infrastructure-error` and a nonzero overall
exit. Invalid model runs are never sent to semantic execution. The standalone
worker script is container implementation code, not a host execution entrypoint.

## Results and interpretation

Integrated results include `semantics.cases` and `semantics.summary`; standalone
runs save the same object as `semantics.json`. Each case records validator/version,
`semanticStatus`, reason and trials. Each trial records seed, scenario, assertions,
diagnostic, runtime, immutable image ID and artifact path. Inputs, expected values
and observations are retained for review.

- `passed`: every trial passed all assertions.
- `failed`: a command was missing/invalid or a trial failed an assertion.
- `not-evaluated`: no validator, no backend requested, or invalid model response.
- `infrastructure-error`: execution/protocol/cleanup could not be verified. If
  mixed with failed trials, this case remains an infrastructure error; individual
  trial assertions remain visible.

Summary reports configured coverage (cases with validators / all selected cases),
evaluated coverage (passed + failed / all selected cases), and pass rate
(passed / evaluated). With no evaluated cases, pass rate is null, not 100%.
Infrastructure errors and skipped cases are separate counts. Semantic failures
and infrastructure errors make the CLI fail after retaining results; the existing
model-run `status` still describes generation/response validation.

Offline verification exercises fixed, repository-owned good and bad commands,
exact JSON/byte assertions, summary accounting, and a mocked container lifecycle.
Its host runner rejects sources outside that fixed list and is not exposed in
the public CLI. Passing offline tests does not establish that a real Docker
backend is provisioned or that a model has passed these cases.
